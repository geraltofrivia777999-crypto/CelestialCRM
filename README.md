# Celestial CRM

Рабочий MVP CRM для арбитражной команды. Исходные `*.dc.html` в корне — это
одновременно визуальные макеты и production-страницы. Docker собирает из них
обычный статический HTML без frontend-фреймворка и без Node.js.

## Стек

- HTML + CSS + обычный JavaScript
- FastAPI + SQLAlchemy 2 + PostgreSQL
- Celery + Redis для Keitaro и долгих операций
- Alembic для миграций
- Docker Compose + Nginx

## Локальный запуск

1. Скопируйте `.env.example` в `.env`.
2. Задайте надёжные `SECRET_KEY`, `FIELD_ENCRYPTION_KEY`, `ADMIN_PASSWORD`.
3. Запустите:

```bash
docker compose up --build
```

CRM будет доступна на `http://localhost:8080`, OpenAPI — на
`http://localhost:8080/api/docs`.

Перед включением Keitaro создайте подключение в «Настройки → Интеграции», выполните
ручной backfill и сверьте дневные клики, конверсии и Revenue. Затем установите
`KEITARO_SYNC_ENABLED=true`.

### Подключение Keitaro

В форме нужен адрес установленного трекера, например
`https://tracker.example.com`. Адрес документации `admin-api.docs.keitaro.io`
не является адресом трекера и отклоняется при сохранении.

После проверки соединения CRM автоматически запускает backfill за 90 дней.
Дальнейшая синхронизация использует перекрывающее окно, идемпотентный upsert и
checkpoint. В Медиаборд попадают:

- `campaign_unique_clicks` → INST;
- `leads` → REG;
- `sales` → FTD;
- `revenue` → Revenue.

SPEND в Медиаборде считается по блоку «Агенты и платёжки» (ТЗ 2.4.4) и Keitaro его
не перезаписывает — `cost` сохраняется только в `external_payload` для сверки.
Поле, заполненное вручную через «Изменить данные», закрепляется за пользователем и
переживает синхронизацию; очистка поля возвращает его под управление Keitaro.

Баер определяется по логину в `Sub ID`, номер которого настраивается у
подключения; резервный способ — совпадение группы кампаний с группой пользователя.
API-ключ хранится в базе только в зашифрованном виде и не возвращается через API.

## Медиаборд

Таблица показывает воронку, затраты и результат. Колонок «Агенты и платёжки» и
«RENT» в ней нет: разбивка по агентам живёт в модалке записи и на итог не
влияет — расход и так виден в SPEND, а RENT в этой команде не используется.

**Порядок колонок перетаскивается.** За верхний ряд заголовка переставляются
блоки целиком, за нижний — колонки внутри своего блока; между блоками колонка
не переезжает, потому что «Revenue» в «Затратах» означала бы не то, что
написано. Порядок запоминается вместе с остальным видом доски. Зашивать его
было нечем: кто-то смотрит сначала затраты, кто-то воронку.

Расход попадает в запись двумя путями — руками через «Изменить данные» и
автоматически из Meta Ads (см. «Фиксация расхода за отрезок дня»). Оба идут
через одну формулу процента агента, поэтому числа сходятся.

## Оффера

Раздел ведёт свой справочник: оффер заводят руками кнопкой «Новый оффер», а не
тянут из Keitaro. Из трекера остаются только списки GEO и партнёрок — так
значения совпадают с Медиабордом и Финансами.

Строки различает `offers.connection_id`: у ручного оффера он пуст, поэтому
синхронизация его не видит и не перезаписывает. Синхронизированные офферы
никуда не делись — они по-прежнему нужны Медиаборду, Финансам и Meta, но на
странице «Оффера» не показываются и через её ручки не редактируются
(`PUT`/`DELETE` на них отвечают 409).

Колонки: звёздочка, название, партнёрка, GEO, CPA, капа, кнопка CapAlert, ТЛы,
баеры, статус. Капа — свободный текст («300 FTD / день», «по договорённости»):
числом её не сделать, команда пишет условие партнёрки как есть. CPA — наоборот
число со своей валютой: с ним оффер уезжает в книгу баера готовым к работе.

### Оффер приезжает в Финансы сам

Назначили баера — строка появляется у него в Финансах за текущий месяц: с
названием, партнёркой, гео и ставкой, плюс пустая строка под оффером для
депозитов. Раньше её заводили руками, и книга расходилась со справочником в
мелочах: то название сокращено, то ставка устарела, то оффер вовсе забыли.

В какую из двух таблиц баера попадёт оффер, решает его гео по справочнику
«Настройки → Тиры стран». Оффер без гео не переносится: тир — это страна, и
угадывать её нельзя.

У строки книги есть ссылка на оффер справочника (`source_offer_id`), поэтому
повторное назначение узнаёт свою строку и обновляет ставку с партнёркой, а не
заводит дубль с тем же названием.

**Связь двусторонняя.** Поменяли в книге гео или ставку — справочник обновится
вместе с ней: правку чаще замечает тот, кто ведёт книгу (партнёрка подняла
ставку, гео связки уточнилось), и без этого следующее назначение того же оффера
привезло бы другому баеру старые числа. Кто и что поправил, видно в журнале
изменений.

Название в обе стороны не синхронизируется: в книге его правят под свою связку,
и переписывать им справочник значило бы терять исходное имя оффера.

Строка между таблицами не переезжает, даже если новое гео другого тира:
депозиты и затраты уже введены в эту таблицу. Несовпадение видно по значку тира
рядом с гео.

Снятый баер свою строку сохраняет: в ней уже могут быть введённые депозиты, и
удалять их из-за перестановки в справочнике нельзя. Прошлые месяцы назначение
тоже не трогает — закрытый месяц не должен меняться задним числом.

### Путь оффера

| Статус | Когда наступает |
| --- | --- |
| Не занят | Оффер только заведён, за ним никого нет |
| Активен | Оффер назначен тимлиду и ждёт, пока тот раздаст его баерам |
| В работе | Тимлид назначил баеров |
| Холд, Стоп | Ставит человек |

Первые три статуса ставит само назначение и снимает тоже оно: снятый последний
баер возвращает оффер тимлиду, снятый последний тимлид — в «Не занят». Холд и
Стоп назначение не перебивает и не сбрасывает — оффер могли остановить по
требованию партнёрки, и баеры при этом остаются на месте. Снять их можно только
руками, выбрав другой статус.

Назначения живут в двух таблицах: `offer_leads` (тимлиды) и `offer_buyers`
(баеры). Обе входят в область видимости: баер видит свои офферы, тимлид — свои
и офферы своих баеров, администратор — весь справочник.

### CapAlert

Кнопка в строке открывает **ту же форму, что и «Утилиты → CapAlert»** — со
всеми полями: несколько офферов, таймзона, тема супергруппы, пороги. Оффер из
строки уже отмечен, название и лимит предзаполнены (лимит — первым числом из
капы). Если на этом оффере капы уже есть, они показаны сверху и открываются на
правку, а не плодят дубли.

Форма одна на обе страницы (`frontend/cap-ui.js`) намеренно: своя урезанная
копия в Офферах однажды разошлась с API — она слала поле `offer_id`, которого
после перехода на несколько офферов уже не существовало, и кнопка молча
перестала работать. Кнопка требует `utilities.manage`; без активного чата
уведомлений окно не открывается и отправляет в «Утилиты».

Сам список кап живёт в «Утилиты → CapAlert»: таблица с названием, метрикой,
периодом, **прогрессом**, порогами и статусом, над ней счётчики Всего /
Активных / Достигнуто и фильтры по статусу и метрике. Прогресс считает сервер
и отдаёт вместе со списком — иначе двадцать кап стоили бы двадцати отдельных
запросов. «Достигнуто» — это про лимит, а не про статус: капа бывает активной
и уже выбранной.

Три вещи в капе, о которых стоит знать:

* **Офферов может быть несколько, и они складываются.** Партнёрка обычно даёт
  общий лимит на связку, а не на каждый оффер по отдельности.
* **У капы своя таймзона.** Счётчик обнуляется в её полночь, а не в полночь
  сервера. По умолчанию подставляется таймзона браузера.
* **Свой `thread_id`.** У канала он тоже есть, но капы одного чата часто
  разводят по разным темам супергруппы.

Периодов четыре: день, неделя, месяц и **общий лимит без сброса**. Последний
нужен потому, что партнёрка часто даёт не «300 в день», а «3000 всего» — дневной
капой такой лимит не выразить, и его пришлось бы сторожить глазами. У него нет
периода, а значит нет и полуночи, в которую что-то обнуляется: счётчик
пройденных порогов там не сбрасывается никогда, и таймзона задаёт только
границу «сегодня».

Таймзона выбирается из списка, который отдаёт сам браузер, — он знает актуальный
набор IANA и не устареет вместе с нашим кодом. Зона, которой браузер не знает,
но которая уже сохранена у капы, остаётся в списке выбранной: иначе сохранение
молча сменило бы её.

Пороги выбираются готовыми значениями — 25, 50, 70, 75, 80, 90, 100 %. Порог,
которого в наборе нет, дорисовывается из самой капы: без этого он исчезал бы из
формы и терялся при первом же сохранении.

### KPI и комментарий

Отдельными столбцами их нет намеренно: это длинный текст, который в таблице
либо режется до бессмысленного огрызка, либо растягивает строку на пол-экрана, а
читают его редко и по одному офферу за раз. Клик по названию оффера раскрывает
блок под строкой.

### Виджет на дашборде

«Рабочие оффера» показывают не всё активное, а то, что ждёт именно этого
человека. Роль читается по правам, а не по названию — переименованная или
скопированная роль ведёт себя так же:

| Кто | Что видит |
| --- | --- |
| Полный доступ | Оффера в статусе «Не занят» — их ещё некому раздать |
| `offers.manage` (тимлид) | Назначенные лично ему и уже «Активные» |
| Остальные (баер) | Назначенные лично ему и ушедшие «В работу» |

## Meta Ads

Модуль закрывает ТЗ 3.2–3.8: кабинеты и статистика, заливы с реальной публикацией
кампаний, шаблоны, креативы и автоправила.

### Права

| Право | Что открывает |
| --- | --- |
| `meta.view` | кабинеты, статистика, заливы и правила на чтение |
| `meta.manage` | подключение Business Manager, токен, ответственные за кабинеты |
| `meta.launch` | заливы, шаблоны, креативы, правила — всё, что тратит бюджет |

Разделение не формальное: `meta.manage` даёт доступ к токену кабинета, а
`meta.launch` — к деньгам на нём, и в команде это обычно разные люди.

### Подключение

Первое подключение делается мастером на странице «Meta Ads» — пять шагов:
инструкция, токен, проверка, выбор кабинетов, готово. На шаге проверки CRM
спрашивает Meta, какие кабинеты видны через токен, и показывает их до того, как
что-либо сохранено. Невыбранные кабинеты заводятся выключенными: они видны в
списке, но синхронизация их не трогает.

Нужен **токен системного пользователя** Business Manager; токен обычного
пользователя живёт слишком мало. Для чтения хватает `ads_read`, для публикации
заливов и действий автоправил нужен `ads_management`, а для верхних уровней
обзора — `business_management` и `pages_show_list`. Без последних двух кабинеты
и статистика работают как раньше, но аккаунты, БМы и фан-пейджи в обзоре будут
пустыми: синхронизация этих трёх шагов не роняет весь прогон. Токен хранится
зашифрованным и через API не возвращается. Сохранение проходит, только если
через токен реально видно хотя бы один рекламный кабинет — иначе первая же
синхронизация упала бы.

`Business ID` необязателен: без него берутся кабинеты, доступные владельцу
токена, с ним — принадлежащие конкретному Business Manager.

### Фиксация расхода за отрезок дня

Баер льёт один оффер с 12:00 до 16:00, потом переключается на другой. Дневная
статистика Meta про это не знает — она отдаёт сумму за сутки, поэтому окно
берётся из почасовой разбивки.

На уровне «Кампании» у строк появляются чекбоксы, а в ряду фильтров — **окно
фиксации**: день и отрезок часов. Порядок такой: выбрать окно → отметить
кампании в таблице → нажать «Фиксация расхода» → выбрать оффер. Агент и баер
там же, баер подставлен свой.

Окно стоит рядом с фильтрами, а не внутри формы: на цифры смотрят и решают, что
относить, до того как открывают форму. Сама форма окно только показывает;
поменяли его при открытой форме — суммы пересчитаются.

Право — `media.manage` или `meta.launch`. Фиксацию делает баер со своего
аккаунта, а `meta.launch` — это заливы, автоправила и деньги в кабинете, и у
роли «Buyer» его нет: требовать его значило бы выдать баеру заодно запуск
рекламы. Ничего нового `media.manage` тут не открывает — этот же расход баер
и так заводит в Медиаборде руками, здесь сумму считает Meta.

Выбор живёт в таблице, а не в форме, потому что относят не «всё, что крутилось
в этот день», а конкретные кампании: одна кампания за день успевает полить
разные офферы, а один оффер набирается из нескольких кампаний. Заодно часы
спрашиваются только по отмеченным — раньше каждое открытие формы дёргало Meta
по всем кампаниям дня.

Рядом с каждой отмеченной кампанией видно расход **за окно** и расход за сутки,
внизу — сумма выбранного. Кампанию можно убрать прямо из формы.

Баер фиксирует расход на себя, и это проверяет сервер: `meta.launch` есть у
всех, кто льёт, и без проверки любой из них мог бы записать свой расход на
чужой день в Медиаборде. Отнести на другого человека может тот, кто и так ведёт
чужие кабинеты (`meta.manage`).

Расход уходит в Медиаборд обычной записью «день + баер + оффер» и ложится на
выбранного агента — процент считает та же формула, что и при ручном вводе.
Иначе два способа завести расход давали бы разные числа.

Три вещи, без которых фиксация была бы опасной:

* **Окно — полуинтервал `[с, до)`.** «С 12:00 по 16:00» — это часы 12, 13, 14
  и 15. Иначе шестнадцатый час попадал бы и в это окно, и в следующее.
* **Один час нельзя отнести дважды.** Занятые часы видны прямо в строке
  кампании, а попытка сохранить пересекающееся окно отклоняется с указанием,
  куда этот кусок уже ушёл. Без этого второй клик по кнопке молча удваивал бы
  расход.
* **Хранится сумма до процента агента.** Процент меняется, и пересчитать
  запись без исходной суммы было бы не из чего.

Привязку можно снять — расход вернётся из записи Медиаборда. Несколько окон
одного дня на один оффер складываются, а не перезаписывают друг друга.

Часы считает сама Meta и только в таймзоне рекламного кабинета — других
вариантов Graph API не даёт, поэтому таймзона написана рядом с числами.

### Обзор: восемь уровней

Вкладка «Обзор» показывает одну и ту же дневную статистику в восьми разрезах —
меняется только ключ группировки. Структура повторяет то, как устроен сам
Facebook:

```
                    фан-пейджи
                        │
социальный аккаунт ─────┼───── БМы ───── рекламные кабинеты ───── кампании
                        │                        │                    │
                        └── фан-пейджи БМа       │                 адсеты
                                                 │                    │
                                        ответственный в CRM      объявления
```

| Уровень | Как собирается | Что в опознавательных колонках |
| --- | --- | --- |
| Пользователи | по кабинетам, закреплённым за человеком | имя |
| Аккаунты | владелец токена | БМы, фан-пейджи, кабинеты — счётчиками |
| Фан-пейджи | по объявлениям: ФП получает расход рекламы, которая крутится от его лица | категория, БМ |
| БМы | по кабинетам БМа | фан-пейджи, кабинеты |
| Кабинеты | сам кабинет | тип (БМ или личный), статус, БМ, ответственный |
| Кампании / Адсеты / Объявления | три уровня Meta как есть | кабинет, статус; у объявления ещё фан-пейдж |

Метрики одинаковые на всех уровнях: расход, показы, клики по ссылке, CR, CPC,
CPM, результаты, CPA. Клики по ссылке хранятся отдельно от общих: в общие Meta
кладёт лайки и развороты текста, а трафик меряют переходами. «Результаты» —
конверсии пикселя кабинета, они не обязаны сходиться с лидами Keitaro, которые
приходят по постбекам партнёрки.

Доход, профит и ROI появляются только на уровне кампании и выше. Ключ атрибуции —
ID кампании Meta в sub_id ссылки, поэтому у адсетов и объявлений дохода нет: он
не делится между ними, и пустые столбцы там просто не показываются.

Объект, который за период ничего не открутил, из обзора не пропадает — строка
остаётся с нулями. Иначе выключенный вчера кабинет выглядел бы как несуществующий.

Ответственный за кабинет назначается прямо в строке уровня «Кабинеты» — это
единственное поле кабинета, которое принадлежит CRM, а не Meta.

### Расход по часам

Клик по строке кампании, адсета или объявления в обзоре открывает окно с
расходом по 24 часам: столбики, пиковый час, итоги и таблица часов, в которых
были деньги.

Данные у нас не хранятся — запрашиваются в Meta по требованию и живут в кеше
пять минут. Почасовую копию всей статистики держать незачем: она в 24 раза
больше дневной, а смотрят её точечно. Кнопка «Обновить» ходит мимо кеша.

Два ограничения, о которых окно говорит прямо:

* **Часы считаются в таймзоне рекламного кабинета.** Других вариантов Graph API
  не даёт, поэтому таймзона написана под графиком: «пик в 19:00» ничего не
  значит, если кабинет живёт в другом поясе.
* **Дни периода складываются в одни сутки.** Выбран период в неделю — столбик
  «19:00» это сумма семи вечеров, а не один конкретный.

Уровни выше кампании (кабинеты, БМы, аккаунты, пользователи) окно не открывают:
у них нет объекта в Meta, к которому можно запросить разбивку.

### Заливы: связки, мастер и очередь

Вкладка «Заливы» делится на три:

**Связки** — заготовки. Связка описывает залив целиком: кампанию, адсет и
объявление. Один раз собрал — заливаешь на любой кабинет.

**Залить связку** — мастер из трёх шагов, чтобы одну связку раскатать сразу на
несколько кабинетов:

1. **Настройки** — выбор связки и время. Справа видно, что именно заливается:
   цель, бюджет, окно конверсии, гео, интересы, плейсменты. «Расширенный режим»
   открывает поля залива — название, оффер, ссылку и тексты можно поменять под
   конкретный пролив, не трогая связку.
2. **Кабинеты** — таблица с выбором, до 25 за раз. Ограничение не бюрократия:
   каждый залив — это три записи в Meta, и пачка на сотню кабинетов упёрлась бы
   в лимит запросов раньше, чем доехала до конца. На кабинет задаются свои
   страница, пиксель, ссылка и бюджет — остальное у пачки общее. Страницы и
   пиксели спрашиваются у Meta в момент, когда кабинет отметили: запрашивать их
   на все видимые кабинеты значило бы полсотни запросов ради трёх нужных.

   Сам ID пикселя связка не хранит: пиксель принадлежит кабинету, и один на всю
   пачку означал бы, что двадцать кабинетов шлют события в чужой. В связке
   остаётся только событие («Лид», «Покупка») — оно про то, что считаем, а не
   про то, куда. Если цель связки считает конверсии, мастер не пустит дальше
   шага «Кабинеты», пока пиксель не выбран у каждого.
3. **Креативы** — объявления и файлы задаются один раз на всю пачку. Файл при
   заливе уходит в каждый выбранный кабинет отдельно: один и тот же файл в
   другом кабинете имеет другой хэш, и чужой Meta не примет.

   «Кол-во адсетов» заводит копии адсета внутри кампании — Meta учится на
   каждой отдельно, и одна обычно раскачивается лучше прочих. «В кампаниях
   разные крео» раздаёт файлы по кабинетам по очереди вместо копирования в
   каждый. «Уникализировать креативы» дописывает в файл случайную метку в
   служебное поле формата: пиксели не меняются, а хэш становится своим в каждом
   кабинете. Формат, который так не умеет, остаётся прежним — портить файл ради
   уникальности хуже.

   **Языки** — это не отдельные объявления, а один креатив с набором текстов:
   Meta показывает зрителю текст на его языке сама (`asset_feed_spec` с
   правилом на язык). По объявлению на язык делило бы бюджет между ними и
   учило каждое отдельно.

Отдельной вкладки «Креативы» нет: файл нужен ровно в момент залива, и держать
его список между заливами незачем — в объявление всё равно попадает то, что уже
лежит в Meta.

Кабинет, не прошедший проверку (например, без креативов), не отменяет
остальные: он возвращается отдельной строкой с причиной, годные уходят в
очередь. Заготовки при этом создаются для всех — иначе после ошибки пришлось бы
заново набивать форму.

**Очередь заливки** — созданные заливы и журнал вызовов Graph API: шаг, залив,
кабинет, ID созданного объекта или текст ошибки, время и статус. Журнал
существует потому, что Meta не поддерживает ключи идемпотентности: единственный
способ понять, что именно успело создаться до обрыва, — писать каждый вызов до
отправки.

У неудавшейся операции есть «Повторить». Публикация идемпотентна по записанным
ID, поэтому повтор продолжает с того шага, на котором всё встало, и второй
кампании не создаёт. Автоповтора нет намеренно: слепой ретрай после неясной
ошибки — прямой путь к дублю, поэтому решение принимает человек.

### Связка

Мастер связки повторяет порядок, в котором её держат в голове: сначала решают,
за что платим, потом кому показываем, потом что показываем.

**Кампании.** Цель, Advantage+, названия, бюджет и стратегия ставок. Целей в
интерфейсе девять, а в Meta их шесть: «Лиды» и «Продажи» — одна цель с разной
оптимизацией, «Отметки Нравится» и «Буст ФП» — тоже. Поэтому связка хранит
пресет цели, а сервер раскладывает его на `objective` и `optimization_goal` при
сохранении: держать их врозь нельзя, иначе они разъедутся при первой же правке.

Тип бюджета выбирает поле, а не заводит вторую сумму: дневной и на весь срок
Meta вместе не принимает. Уровень бюджета решает, где он живёт — на кампании
(Meta распределяет его между адсетами сама) или на адсете (расход остаётся там,
где его поставили).

**Адсеты.** Событие пикселя, окно конверсии, аудитория, демография, гео,
интересы, плейсменты и устройства. Тип локации по умолчанию — «Проживающие»:
для товарки турист в стране бесполезен. Advantage+ аудитория и ручное расширение
таргетинга вместе не отправляются — Meta принимает что-то одно, а Advantage+ уже
означает «ищи шире заданного».

У версий ОС есть только нижняя граница: в `user_os` Meta принимает «версия и
выше», поля под верхнюю границу в Graph API нет.

**Объявления.** Названия, тексты, кнопка, Advantage+ для креативов. Тексты
допускают spintax — `{Купи|Закажи} сегодня`. Разворачивается он при публикации,
по варианту на объявление: смысл spintax в том, что у каждого объявления свой
текст, а связка одна на все.

Названия кампании, адсета и объявления — шаблоны с макросами. Списком с
расшифровками они открываются кнопкой «Макросы» рядом с полем: макросов два
десятка, и `{{cab.time}}` без пояснения ни о чём не говорит.

Наборы по уровням разные, и это не придирка: `{{campaign.id}}` можно подставить
в название адсета — кампания к тому моменту уже создана, — а в название самой
кампании нельзя, ID Meta присваивает после создания. Показывать макрос, который
гарантированно останется пустым, значит обещать то, чего не будет.

Считаются макросы на сервере: заливов из одной связки бывает двадцать, и номер
адсета должен быть номером внутри своего залива. У случайных наборов длина
задаётся последним числом — `{{random.digits.6}}`, `{{random.letters.en.4}}`.
Неизвестный макрос выбрасывается, а не остаётся в тексте — в кабинете он
выглядел бы опечаткой, а чинить её пришлось бы уже в Meta.

Языки и интересы ищутся прямо в Meta: поле с поиском ходит в её targeting
search её же токеном и показывает найденное с путём вроде «Интересы /
Дополнительные интересы» — по одному названию интересы не различить, их тысячи.
Своего справочника здесь быть не может: интересы Meta заводит и переименовывает
сама, а её ID — единственное, что она принимает в `flexible_spec`. Запрос уходит
после паузы в наборе и от двух символов: на один символ Meta отдаёт случайную
выборку, и показывать её как подсказку — значит предлагать наугад.

Страны берутся из своего справочника: коды стран не меняются, и гонять за ними
в Meta на каждый символ незачем. Ищутся они и по коду, и по русскому названию, и
по английскому — страну набирают то «DE», то «Герм», то «Germ».

Особых категорий рекламы три — кредиты, жильё и работа. Политики и азартных игр
в `special_ad_categories` рекламного кабинета нет, они живут в отдельном
согласовании, и выбор, который Meta не примет, был бы обещанием, а не настройкой.

### Время залива

Блок «Время» в мастере отвечает на два разных вопроса. «Дата залива» — когда
создавать объекты в кабинете; «Запускать» — когда им начать крутиться. Залить
ночью и стартовать в полночь понедельника — обычная просьба.

Запланированный залив ставит в очередь планировщик, когда придёт время, а не
отложенная задача в брокере: задача с eta на завтра не переживёт перезапуск
воркера, и залив просто не состоится — молча. Проверка идёт раз в минуту, время
снимается с залива до отправки, иначе следующий тик поставил бы его второй раз.

Пауза между кабинетами разносит заливы по времени: двадцать кабинетов,
стартующих в одну секунду с одним креативом, — это ровно тот след, из-за
которого прилетает бан. Первый уходит сразу, каждый следующий — через
заданный интервал.

Тумблеры пауз решают, что оставить на паузе после публикации. Уровни снимаются
снизу вверх — объявления, адсет, кампания: если оборвётся на середине, крутиться
не начнёт ничего, потому что верхний уровень всё ещё на паузе.

### Что проверяется до обращения к Meta

Ошибку, которую Meta вернёт кодом 100, дешевле поймать у себя: её текст обычно
говорит «invalid parameter», а какой именно — приходится угадывать. Поэтому до
первого запроса залив проверяется на:

* ссылку, страницу Facebook, бюджет больше нуля и хотя бы один креатив;
* креатив из чужого кабинета и видео без превью — без превью Meta не соберёт
  `video_data`;
* пиксель для целей с конверсиями, страницу для лайков страницы и переписок —
  Meta требует под каждую цель свой промо-объект;
* дату окончания при бюджете «на весь срок» — без неё Meta не знает, на сколько
  дней его растянуть;
* особую категорию рекламы против таргетинга: она запрещает пол, возраст вне
  18–65 и исключения.

Цель «Установки приложения» пока отбивается на этой же проверке: Meta требует ID
приложения и ссылку на стор, а связка их не хранит. Лучше сказать это словами,
чем отдать залив и получить ошибку про `promoted_object`.

### Заливы и публикация

Залив — учётная запись команды (оффер, GEO, партнёрка, ответственный, бюджет,
даты) и одновременно рецепт публикации. Публикация идёт этапами: кампания →
группа объявлений → объявления, по одному на креатив. ID каждого созданного
объекта сразу записывается в залив, поэтому повторный запуск после сбоя
продолжает с места обрыва, а не создаёт вторую кампанию — ключей идемпотентности
Meta не поддерживает, и эта запись единственная защита.

Бюджеты уходят в Meta целыми минорными единицами, но не во всех валютах они
есть: в иене и воне «центов» нет, и умножение на сто дало бы кабинету
стократный бюджет. Список таких валют зашит отдельно.

Версия ОС уезжает строкой вида `iOS_ver_13.0_and_above` — без `_ver_` Meta
отбивает адсет. Окно атрибуции отправляется только тем целям, у которых оно
есть: у охвата не бывает «конверсии в течение семи дней».

Рандомизация бюджета и возраста считается от ID залива, а не случайно при каждом
запуске: иначе повтор после сбоя ушёл бы в кабинет с другими числами.

Всё создаётся **на паузе**. Снятие с паузы — отдельный шаг и отдельная запись в
журнале операций: именно в этот момент начинают тратиться деньги. Каждый вызов
Graph API пишется в `meta_operations` до отправки и дополняется после ответа.

Оборванный POST не повторяется автоматически: ответ мог потеряться уже после
того, как Meta создала объект. Повторяются только запросы, отбитые по лимиту, —
там точно ничего не произошло.

### Автоправила

Правило считается по нашим числам, а не средствами Meta: ROI и цену лида Meta не
знает.

Правило описывается пятью вопросами:

| Поле | Что задаёт |
| --- | --- |
| С чем работать | Кампания, адсет или объявление — к объекту этого уровня применится действие |
| Какие статусы брать | Активные, на паузе или любые |
| Период статы | Сегодня, вчера, последние 3 / 7 / 30 дней |
| Частота проверки | От раза в 15 минут до раза в сутки |
| Что делать | Уведомить, остановить, запустить, поднять или снизить бюджет |

Условий может быть несколько, и они соединяются И: «ROI < −30 И расход ≥ 50».
Операторы — `<`, `≤`, `>`, `≥`, `=`. Пустой список условий разрешён намеренно:
«остановить все активные объявления» — осмысленное правило, у которого условий
нет. Но такое правило с действием сложнее уведомления просит подтверждения при
сохранении, чтобы «остановить всё» не проскочило по невнимательности.

Порог минимального расхода остаётся у каждого правила — без него первая же
кампания с двумя кликами выглядит убыточной, — как и пауза между
срабатываниями: иначе правило «поднять бюджет на 20 %» удвоит его за час.
Частота и пауза — разные вещи: первая говорит, когда смотреть, вторая — как
скоро можно сработать по тому же объекту ещё раз.

Два ограничения, которые следуют из данных, а не из осторожности:

* **Доход есть только на кампании.** Он приходит из Keitaro по ID кампании,
  поэтому на адсетах и объявлениях ROI, профит и цена лида неизвестны, и
  правило по ним там молчит. Не «равно нулю» — именно неизвестно.
* **У объявления нет своего бюджета.** Он живёт на адсете или на кампании,
  поэтому правило «изменить бюджет» на уровне объявления не сохраняется.

Объект, статуса которого мы ещё не знаем (статистика приехала раньше
синхронизации объектов), проходит только в режиме «Любые» — иначе правило
действовало бы вслепую.

Кнопка «Что сработает» показывает, по каким объектам правило сработало бы
сейчас и с какими значениями, ничего не выполняя. Расписание включается флагом
`META_RULES_ENABLED` — отдельно от синхронизации и намеренно выключено по
умолчанию.

### Доход и ROI по кампаниям

Meta не знает про выплаты партнёрки, поэтому доход присоединяется из Keitaro по
ID кампании Meta. Чтобы он появился:

1. в ссылке трекера проставьте `sub_id_N={{campaign.id}}` — Meta подставит ID сама;
2. этот же номер `N` укажите в подключении в поле «sub_id с ID кампании».

Пока номер не настроен, доход, профит и ROI показываются прочерком — ноль здесь
означал бы «слили в минус», а не «не знаем».

Ответственный за кабинет назначается в CRM и определяет видимость: баер видит
кабинеты, закреплённые за ним и за его людьми, кабинет без ответственного —
только руководство.

Расписание включается флагом `META_SYNC_ENABLED=true`; окно синхронизации всегда
перекрывает минимум три дня, потому что Meta досчитывает атрибуцию задним числом.

### Токен Meta: три способа и почему это важно

На запросы к Graph API способ получения токена не влияет — она принимает любой
одинаково. Влияет он на то, сколько токен проживёт, поэтому подключение помнит,
чем он выпущен, и говорит об этом, когда синхронизация встанет.

| Способ | Живёт | Когда брать |
| --- | --- | --- |
| **System User** | Бессрочно, если при выпуске выбрать «Never» | Основной способ для команды |
| **Токен сессии (EAAB)** | Пока жива сессия аккаунта | Когда доступа к Business Manager нет или нужно быстро проверить кабинет |
| **Токен приложения** | Часы | Разовая проверка, не для синхронизации |

Токен сессии обнуляют смена пароля, выход из устройств и запрос подтверждения
личности, поэтому вставлять новый придётся регулярно. Meta считает использование
токенов своих внутренних приложений нарушением условий — блокируют при этом
обычно не токен, а Business Manager. Способ рабочий, но держать на нём всю
команду вместо системного пользователя не стоит.

Кнопка **«Проверить доступы»** в подключении показывает, что этим токеном
реально доступно: кабинеты, Business Manager, фан-пейджи, кампании и пиксели —
каждый пункт отдельной строкой с ошибкой Meta, если он закрыт. Проверяем
пробными вызовами, а не `debug_token`: у токена из сессии приложение чужое, его
секрета у нас нет, и посмотреть права официальным способом невозможно. Запрос,
который прошёл, — единственное надёжное доказательство доступа.

## Утилиты

Модуль 9 ТЗ: два раздела на одной странице — «Alert» и «CAP», плюс каналы и
журнал. Всё уходит в Telegram.

**Бот.** Один на воркспейс: у команды один бот и несколько чатов, а не наоборот.
Токен сохраняется, только если Telegram его принял — токен с опечаткой иначе
лежал бы молча и подвёл в момент, когда алерт действительно нужен. Хранится
зашифрованным и через API не возвращается: по нему можно писать от имени
команды в любой чат, куда бота добавили.

**Каналы** — чаты, куда идут уведомления. Добавить бота в группу мало: CRM не
знает, в какой из чатов писать, поэтому чат заводится каналом и у него
указывается `chat_id`. Искать его руками не нужно — кнопка «Найти чаты» в форме
канала спрашивает у Telegram, где бота видели за последние сутки, и подставляет
и название, и `chat_id`. Список пуст, если у бота настроен вебхук или с момента
добавления прошло больше суток; тогда достаточно написать в группу любое
сообщение и нажать кнопку ещё раз.

У супергруппы можно указать тему, иначе алерты по CAP сыпались бы в общий чат.
Кнопка «Проверить» отправляет пробное сообщение: Bot API не подтверждает доступ
к чату иначе, чем доставкой.

**Alert (9.1).** Триггер срабатывает, когда сошлись условия; расписание шлёт
сводку в заданное время. Правило собирается из трёх частей: область, период и
условия.

**Область** решает, по какому ключу режется период — одно число на всю команду,
строка на каждый оффер, баера, страну или на объект Meta:

| Область | Источник | Что считается |
| --- | --- | --- |
| Глобально, по офферам, по баерам | Медиаборд | деньги и события трекера |
| По странам | Медиаборд | GEO берётся из карточки оффера |
| По кампаниям Meta | Meta + Keitaro | закупка и доход по атрибуции |
| По адсетам, по объявлениям Meta | Meta | только закупка |

Источники разные, и поля у них разные: Медиаборд знает депозиты и доход, но не
знает показов и кликов, а кабинет — наоборот. Поэтому каталог полей меняется
вместе с областью, а поле, которого в ней нет, форма подсвечивает и не даёт
сохранить. Ниже кампании доходных полей нет вовсе — атрибуция Keitaro привязана
к ID кампании, и правило по ROI на объявлениях молчало бы вечно.

**Условия** — дерево И/ИЛИ с одним вложенным уровнем: «ROI ниже 20 И (расход
выше 500 ИЛИ лидов больше 10)». Глубже нельзя намеренно — три уровня скобок
никто не проверит глазами перед тем, как пустить правило в общий чат. Поля
сгруппированы по категориям: трафик, трекер, экономика.

Сработавшие строки уходят **одним сообщением** списком, а не по сообщению на
строку: правило «по объявлениям» иначе высыпало бы в чат сотню сообщений
подряд. В сообщение попадают первые двадцать строк по расходу, остальные
сворачиваются в «и ещё N». Показываются те поля, о которых правило и написано.

Кнопка «Проверить» в форме считает ещё не сохранённое правило на сегодняшних
цифрах и показывает, что именно уйдёт в чат. «Что сейчас» делает то же для
сохранённого. У триггера есть пауза между срабатываниями: без неё «расход выше
500» писал бы в чат на каждом прогоне до конца суток.

Показатель без данных — это «неизвестно», а не ноль: ROI без расхода не
посчитан, и условие на нём не срабатывает.

**CAP (9.2).** Лимит по офферу или человеку за день, неделю или месяц. Пороги
задаются в процентах (например 80 и 100): команде нужно знать не только про
исчерпанный кап, но и про подходящий, пока ещё можно перелить трафик. Один и
тот же порог не приходит дважды за период, а со сменой периода счётчик
обнуляется.

**Журнал** пишет каждое уведомление вместе с причиной, если оно не ушло. Когда
в чате пусто, это единственный способ отличить «правило не сработало» от
«Telegram не принял».

Расписание включается флагом `ALERTS_ENABLED` и намеренно выключено по
умолчанию: непроверенное правило пишет в общий чат команды, и первое же ложное
срабатывание стоит доверия к разделу. Частота прогона — `ALERTS_INTERVAL_MINUTES`
(по умолчанию 5 минут); время отправки сводок задаётся в UTC.

Значение фильтра выбирается **одно**: фильтр читают как «поле — условие —
значение», и набор галочек в третьей клетке этой фразы ей не соответствовал.
Список рисует общий компонент выпадающих списков — с поиском и панелью на весь
доступный экран, а не своим маленьким поповером.

Сообщения уходят с разметкой HTML: команда пишет в шаблонах `<b>`, `<code>` и
`<blockquote>`, и без `parse_mode` они приезжали в чат текстом. Значения
макросов при подстановке экранируются — угловая скобка в названии оффера
остаётся текстом и разбор не ломает. Если тег в шаблоне всё же не закрыт,
сообщение уходит вторым заходом без разметки: уведомление важнее оформления.

Права: `utilities.view` — читать правила и журнал, `utilities.manage` — менять и
отправлять пробные сообщения.

## Финансы

Финансы устроены как набор листов одной месячной книги. В шапке один селектор
с тремя группами: общая и две тир-сводки, команды, книги отдельных баеров.
Выбранный лист хранится в `user_preferences`, поэтому рост числа команд не
превращает шапку в бесконечный ряд вкладок и не сбрасывает рабочий контекст при
возврате на страницу.

### Две таблицы у баера

У каждого баера на месяц заведены **две таблицы: Tier1 и Tier2/3**, и
заполняются они по отдельности. Спенд по тирам приходит из разных кабинетов
разными суммами: пока таблица была одна, разделить общий дневной расход между
тирами было нечем, кроме пропорции по доходу, — а пропорция в отчёте о деньгах
читается как замер. Теперь в сводках стоят фактические числа.

Переключатель стоит под именем баера: по умолчанию открыта **общая сводка** —
только чтение, обе таблицы вместе. Заполняют в Tier1 и Tier2/3.

Каждая таблица ведёт свой долг и свою зарплату: минус Tier2/3 не гасится
прибылью Tier1, ступень сетки считается от профита каждой книги отдельно.
Модуль «Расчет ЗП» считает так же — базы приходят частями, по книге на тир,
поэтому расшифровка и Финансы не могут разойтись.

Гео у оффера остаётся, но на разрез уже не влияет: тир задаёт сама таблица.
Справочник «Настройки → Тиры стран» подписывает страну рядом с гео и помогает
понять, в какую таблицу заносить оффер.

### Тиры стран

Вкладка в настройках держит две таблицы — Tier1 и всё остальное — со строками
«код, страна» и кнопкой переноса. Плитками это уже было: страну ищут глазами по
алфавиту, и ровная колонка читается быстрее, чем плашки разной ширины.

Хранится только Tier1: страна без строки считается Tier2/3, и держать вторую
сотню записей ради одного и того же ответа незачем. Базовый список (США, Канада,
Западная Европа, Австралия, Япония, Корея, Сингапур, ОАЭ, Израиль, Саудовская
Аравия — 30 стран) заводится при установке и дальше правится руками: сегодня
партнёрка считает Португалию первым тиром, завтра нет.

Правка справочника меняет только разрезы сводки. Профит, ROI и зарплата от тира
не зависят и пересчёта не требуют.

Спенд и Costs вводятся на день таблицы целиком — построчный ввод внутри каждого
оффера команда попробовала и отвергла: спенд приходит из кабинета одной суммой
за день, и разносить его по офферам руками дороже получаемой точности.

Разрез по тирам — это группировка таблиц, а не деление чисел внутри одной.
Никаких долей и пропорций: сколько ввели в Tier1, столько в Tier1 и стоит.

Дни в сводке — та же сетка, в которой данные и заполняют: показатели строками,
дни столбцами, слева «За месяц». Сводку сверяют с книгой глазами, и список из
тридцати строк для этого не годится.

`GET /finance/summary` собирает общую, тир- и командную сводки одним путём.
Карточки, строки по дням, тирам и баерам агрегируют результат
`services/finance_books.totals()`: отдельной формулы профита или ROI у отчёта
нет. Общая и командная сводки показывают разбивку по тирам: в общей она
объясняет результат компании, в командной — вклад Tier1, Tier2/3 и
непривязанных строк именно этой ветки. В самих тир-сводках таблица не
повторяется, потому что там весь экран уже отфильтрован до одного тира. Область
видимости берётся из той же иерархии `accessible_user_ids()`, что и книга;
чужая команда отвечает 404, чтобы не раскрывать даже её наличие.
Название команды хранится у тимлида (`users.team_name`) и редактируется прямо
в дереве «Команда → Иерархия команды».

Фонд ЗП не вводится и не пересчитывается Финансами. И сводка, и
`GET /salary/calculate` вызывают общий `services.salary.payroll()`, поэтому
расшифровка по людям и итог фонда не могут разойтись.

Фонд живёт только в общей сводке. В тир-сводках его нет, потому что зарплата
человека не делится между его офферами: два таких фонда не сложились бы обратно
в общий. В командной — потому что зарплату ведёт финансист по всей компании
сразу, а не по веткам.

Фонд разложен по ролям той же таблицей, что команда вела у себя: колонка на
роль («ЗП Баеров», «ЗП ТЛов», «ЗП СМО»), строка на тир. У СМО тира нет — он
смотрит за всеми командами сразу, поэтому его сумма стоит одной ячейкой на всю
колонку. «Другие роли» появляются, только если по ним что-то начислено.

Дальше идут два отдельных блока — «ЗП по тирам» и «ЗП по людям». Раньше они
шли встык под фондом и читались как одна таблица.

В блоке «ЗП по тирам» видно, сколько фонда пришлось на Tier1,
сколько на Tier2/3 и сколько на «Вне тиров». В тир попадает только то, что
посчиталось от профита книги этого тира; фикс, вычеты и проценты от профита
команды к тиру не относятся и уходят в отдельную строку — иначе три числа в
таблице не складывались бы в четвёртое. Строка «ЗП итого» равна фонду.

Карточки фонда показываются всегда, даже нулевые: «Баеры · Tier1»,
«Баеры · Tier2/3», «Тимлиды · Tier1», «Тимлиды · Tier2/3» и «CMO». Пустая
карточка отвечает на вопрос «а где CMO», ненарисованная — нет. Строка «Без тира»
появляется, только если в ней есть деньги, чтобы человек без тира не выпал из
фонда молча.

Если у пользователя нет `salary.view`, сводка остаётся доступной, но блок ЗП не
возвращается: право на финансовые показатели не должно автоматически раскрывать
выплаты сотрудникам.

## Расчет ЗП

«Настройки → Расчет ЗП». Правило состоит из компонентов, потому что одной
строкой реальная договорённость не описывается: у баера процент от профита, у
тимлида сверху сетка по профиту команды, у кого-то ещё фиксированный оклад и
вычет. Компоненты складываются.

| Компонент | Что задаёт |
| --- | --- |
| Процент | ставка от выбранной базы |
| Фикс | сумма, не зависящая от показателей |
| Сетка | уровни «до суммы → процент» |
| Вычет | фиксированная сумма или процент от базы, со знаком минус |

Баз три — **«Профит (Финансы)»**, **«Профит команды (Финансы)»** и **«Весь
профит (Финансы)»**. Все читаются из книг Финансов, той же формулой, которую
финансист видит на экране: считать зарплату от показателя, которого нет на
экране, некому проверить.

* профит — своя книга человека;
* профит команды — его книги и книги всех подчинённых по ветке;
* весь профит — книги всех баеров компании. Это база CMO: он ведёт не свою
  книгу и не одну ветку, а все команды сразу.

Профит везде приходит частями — по книге на каждый тир, — и процент со ступенью
применяются к каждой части. По сумме ступень получилась бы выше, и зарплата
разошлась бы с той, что показывают сами Финансы.

Сетка берёт ставку от суммы **целиком**, а не по частям: на границе меняется вся
ставка сразу. Это правило команды, оно же зашито в шкалу по умолчанию.

Правило привязывается к роли или к конкретному человеку; именное сильнее
ролевого. Режим решает, что делать с ролевым правилом: «заменить» отбрасывает
его целиком, «дополнить» добавляет свои компоненты к уже собранным.

**Правило применяется в Финансах.** Открыв книгу баера, финансист видит блок
«Шкала зарплаты» с уровнями его правила и зарплату, посчитанную по ним. Пока
правила на этого человека нет, работает прежняя лестница 10/15/20/25/30 % —
поэтому включение правил не меняет задним числом месяцы, которые никто не
настраивал.

Разделение обязанностей внутри книги: части правила, зависящие от профита самой
книги (сетка и процент), пересчитываются в браузере на каждое нажатие клавиши;
всё остальное — фикс, вычеты, проценты от профита команды — сервер присылает
одной суммой, потому что от правки этой книги оно не меняется.

Кнопка «Рассчитать» в Настройках показывает, что получится у каждого за
выбранный месяц, с расшифровкой каждой строки, и ничего не записывает: это
проверка правил, а не выплата.

Права отдельные: `salary.view` — читать правила и расчёт, `salary.manage` —
менять. Не через `settings.manage`: доступ к комиссиям агентов и доступ к чужим
зарплатам — разные вещи.

## Подтверждения

Все вопросы «точно удалить?» и ввод вроде «в какую колонку перенести задачи»
показываются модалкой CRM, а не окнами браузера. Штатный `window.confirm`
рисуется у верхней кромки экрана и подписан адресом сервера — поверх карточки
задачи это выглядит как сообщение постороннего сайта, а не как действие внутри
CRM.

Диалог живёт в `frontend/navigation.js` и доступен как
`CelestialShell.confirm/prompt/notify`. Контракт тот же, что у браузерных
функций, только ответ приходит промисом, поэтому вызывающий код должен его
дождаться. Кнопка необратимого действия красная, Esc и клик мимо карточки
считаются отказом, фокус возвращается туда, откуда пришёл.

## Выпадающие списки

По той же причине заменён и список у `<select>`: само поле мы стилизуем давно,
а список по клику рисует операционная система — системный шрифт, синяя
подсветка, острые углы поверх нашей формы.

`frontend/select-ui.js` перехватывает открытие и рисует свой список. Поле при
этом остаётся родным `<select>` со своими классами, размерами и значением:
страницы не переписывались, весь код по-прежнему читает `.value` и слушает
`change`. От восьми пунктов появляется поиск — офферов и людей в списках сотни,
и пролистывать такой перечень глазами бесполезно. Работают стрелки, Enter, Esc
и поиск с клавиатуры; `data-native-select` на поле возвращает родное поведение.

Панель прибита к окну, а не к полю: формы лежат в модалках с прокруткой, и
внутри них список обрезался бы их краем.

Там же, в `frontend/responsive.css`, живут `.row-side` / `.row-status` /
`.row-btn` — правая колонка карточек-строк. Раньше каждая страница собирала её
сама, и статус оказывался то выше кнопок, то ниже: контейнер выравнивал по
верху, а бейдж — по центру.

## Финансовый импорт

CSV/XLSX должен содержать колонки:

`date,buyer_login,offer_external_id,link,rent,spend,qual,revenue,salary`

Повторный импорт с тем же `date + buyer + offer + link` обновляет запись.

## Задачи и База знаний

Это два самостоятельных раздела меню, а не вкладки внутри общей страницы:
«Задачи» — `Tasks.dc.html`, «База знаний» — `Knowledge.dc.html`. Разделять их
пришлось потому, что права на них разные, и раздел, закрытый по правам, должен
просто исчезать из меню, а не превращаться в неактивную вкладку. Общий модуль
`frontend/workspace-ui.js` определяет открытую страницу по разметке; API остался
единым (`/api/v1/workspace`, `/api/v1/knowledge`).

Колонки канбана делят ширину доски поровну и тянутся до низа экрана — пустая
колонка остаётся полноценной целью для перетаскивания. Ниже 180 px они не
сжимаются: если колонок много, доска прокручивается по горизонтали, а карточка
остаётся читаемой.

### Как работать с доской

Доска устроена как в Notion: то, что делают часто, делается на месте, а полная
карточка открывается, когда нужна.

| Действие | Как |
| --- | --- |
| Завести задачу | «+ Задача» внизу колонки: название набирают прямо в ней, Enter — создать, поле остаётся открытым для следующей |
| Изменить приоритет, перенести, продублировать, удалить | «⋯» на карточке или правая кнопка мыши |
| Свернуть колонку | «‹» в её шапке; свёрнутая остаётся целью для перетаскивания, клик разворачивает |
| Найти своё | «Мои задачи» рядом со счётчиком |
| Клавиши | `N` — новая задача, `/` — поиск, `Cmd/Ctrl+Enter` — сохранить карточку, `Esc` — закрыть |

Быстрое добавление отправляет только название. Если на доске есть обязательное
поле, показанное во всех задачах, одним названием задача не создастся — тогда
вместо ошибки открывается полная карточка с уже вписанным названием.

Значения полей выводятся на карточке чипами: метка — сама по себе, у остальных
типов рядом остаётся имя поля, иначе «12 000» на карточке ничего не значит.
Больше пяти чипов карточка не показывает, остальное сворачивается в «+N»:
доска нужна, чтобы окинуть взглядом колонку, а не прочитать каждую задачу.

При перетаскивании видна линия вставки — карточка ляжет ровно туда, а не
куда-то в колонку. Перетаскивание работает только в режиме «Мой порядок»: в
отсортированном списке место, куда бросили, всё равно не сохранилось бы.

Фильтр по исполнителю, приоритету и сортировка запоминаются в браузере.
Не запоминаются две вещи: текст поиска — он всегда про «сейчас», и фильтр по
колонке — он повторяет то, что и так видно на доске, а удалённая колонка
оставила бы фильтр, о котором нельзя догадаться.

Пользователь с `workspace.view` может создавать задачи и менять созданные им
либо назначенные на него карточки; `workspace.manage` дополнительно разрешает
управлять всей доской, колонками, полями, шаблонами и разделами. База знаний
отдельно проверяет `knowledge.view`/`knowledge.manage` и наследуемые права роли
на раздел.

### Разделы доски

Доска делится по отделам: «Дизайнеры», «Баеры», «Общие задачи». Разделы — это
полоса вкладок рядом с заголовком; открытый раздел запоминается в браузере,
потому что человек работает в своём отделе, а не выбирает его каждое утро.

Раздел хранит только свои карточки и свои права. Колонки, пользовательские поля
и шаблоны остаются общими на воркспейс — так все разделы устроены одинаково, и
поле, заведённое один раз, работает везде. Порядок карточек считается внутри
раздела: у каждого отдела своя очередь в каждой колонке.

Доступ настраивается шестерёнкой на активной вкладке (нужен `workspace.manage`)
и устроен как в базе знаний: правило адресуется роли или человеку, именное
сильнее ролевого. Раздел, где не отмечен никто, открыт всей команде — иначе
появление разделов отняло бы у команды доску, которой она пользовалась до сих
пор. Достаточно отметить одного адресата, чтобы раздел стал доступен только
отмеченным.

Права раздела: просмотр, создание, правка чужих, удаление чужих. Последние два
именно про чужие карточки — свои и те, где ты исполнитель, правит автор с
исполнителем и без них. Так тимлид отдела ведёт доску отдела, не получая власти
над всем воркспейсом.

Перенос задачи в другой раздел — поле «Раздел» в карточке; оно появляется,
когда разделов больше одного, и требует права создавать в разделе-получателе:
перенос это и есть создание карточки на чужой доске. Раздел с задачами не
удаляется молча — задачи переезжают в другой; последний раздел не удаляется
вовсе, карточке было бы некуда лечь.

### Пользовательские поля и шаблоны

Поле задачи бывает одиннадцати типов: текст, многострочный текст, выпадающий
список, метки (несколько значений), дата, число, сумма, чекбокс, пользователь,
ссылка и файлы. Тип после создания не меняется — уже заполненные значения после
смены типа стали бы мусором, а молча терять их нельзя.

Поле либо общее для доски («показывать во всех задачах»), либо появляется
только в задачах тех шаблонов, куда его добавили. Без этого бриф на креатив
(вид, ГЕО, формат, количество, исходник, референс, ТЗ) висел бы в каждой
карточке, включая задачи бухгалтерии.

Шаблон задаёт набор полей и их порядок — бриф читают сверху вниз, порядок
меняется перетаскиванием. Стандартных полей карточки (название, приоритет,
колонка, срок, описание, исполнители) в шаблоне нет: их всё равно заполняют под
конкретную задачу, а подставленное «Крео для » приходилось стирать перед каждым
вводом.

В списке шаблона — только его собственные поля, и добавляются они одной
кнопкой «Создать поле». Раньше там лежали все поля воркспейса с галочками, и
новый шаблон открывался готовым списком чужих полей от предыдущего брифа:
чтобы собрать свой, надо было сначала разобраться, что из этого не твоё.
Крестик удаляет поле — с подтверждением, в котором сказано, что значения
пропадут из всех задач.

Один шаблон можно сделать **шаблоном по умолчанию** — новая задача сразу
открывается с ним. По умолчанию он ровно один: два означали бы, что форма
открывается то с одним брифом, то с другим, поэтому отметка снимается с
прежнего сама.

Поля брифа в карточке идут одним столбцом, подпись слева от значения:
это анкета, её читают строками. Обязательность помечена звёздочкой у названия —
подпись «обязательное поле» под каждым полем повторялась столько раз, сколько
полей в брифе, и всё равно ничего не сообщала: о незаполненном говорит
сообщение при сохранении.

Отдельного справочника полей нет. Поле заводится там, где понадобилось: в
шаблоне — и тогда оно принадлежит этому шаблону, или прямо в карточке задачи —
и тогда становится общим для доски. Отдельная вкладка «Поля» заставляла выйти
из формы, создать поле и вернуться, чтобы его отметить.

Обязательное поле проверяется только в тех карточках, где оно показано: иначе
поле одного шаблона запрещало бы сохранять задачи всех остальных. Поле с уже
заполненным значением остаётся в карточке, даже если его убрали из шаблона, —
иначе значение продолжало бы лежать в базе, но его нельзя было бы ни увидеть,
ни стереть.

Метки выбираются чипами в строку, а не столбиком чекбоксов: у поля вроде ГЕО
вариантов десятки, и списком они занимали весь экран. Когда вариантов больше
двенадцати, над чипами появляется поиск.

Карточки сортируются по своему порядку, сроку, приоритету, дате создания и дате
изменения — в обе стороны, **у каждой колонки своя**. Общая на всю доску не
годилась: колонки живут по-разному. В «Открыта» смотрят, что горит по сроку, в
«Готово» — что закрыли последним, а в «В работе» порядок расставлен руками, и
любая сортировка его прячет; одним переключателем одно из трёх всегда было
неправильным. Выбор колонки запоминается между заходами.

Перетаскивать карточки можно из любой колонки, включая отсортированную: колонку
задаче меняют независимо от того, как внутри разложены строки. Не работает
только перестановка **внутри** отсортированной колонки — там порядок считает
сортировка, и карточка вернулась бы на место при первой же перерисовке. Поэтому
в такой колонке не показывается и линия вставки: она обещала бы порядок,
которого не будет.

Считается сортировка в браузере: доска уже пришла целиком, и гонять запрос ради
перестановки двадцати карточек незачем.

Сумма хранится строкой с двумя знаками, а не числом с плавающей точкой: это
деньги, и расхождение всплыло бы в отчёте, а не в тесте. Валюта настраивается у
поля.

Доступ к разделу настраивается на роль или на конкретного человека. Именное
правило сильнее ролевого: раздел «только для Ирины» описывается одним правилом
на человека, а не ролью под одного человека. Как только у раздела появилось хоть
одно явное правило, все, кого оно не касается, теряют к нему доступ — поэтому
достаточно отметить одного человека, чтобы папка стала видна только ему.
Правила наследуются вниз по дереву; раздел без единого правила во всей ветке
открыт всем, у кого есть `knowledge.view`. Администратор видит всё всегда —
иначе одним правилом можно было бы запереть себя снаружи.

Разделы базы знаний сворачиваются. У свёрнутого раздела показано число
вложенных статей и подразделов — иначе непонятно, пустой он или просто закрыт.
Свёрнутое запоминается в браузере: дерево — это навигация, раскрывать её заново
после каждой перезагрузки никто не станет. Статья, открытая из поиска,
раскрывает свой раздел сама, иначе её не было бы видно в дереве.

Файлы полей типа «Файлы» лежат в том же хранилище, что и вложения статей, и
отдаются через API с проверкой прав. Файл закрепляется за задачей при
сохранении карточки; незакреплённый удаляется фоновой уборкой. Убранный из
поля, удалённый вместе с полем или вместе с задачей файл стирается с диска
сразу — иначе он навсегда остался бы в квоте воркспейса, не показываясь нигде.

Не реализованы типы Formula, Summary, Progress Updates и Relationship: каждому
нужен свой движок (вычисления по другим полям, агрегаты по подзадачам, связи
между карточками), и это отдельная задача, а не ещё один вариант поля.

Вложения хранятся в постоянном Docker-томе `uploads_data`. По умолчанию лимит
одного файла — 20 МБ, общий лимит воркспейса — 2 ГБ, а незакреплённый за статьёй
файл удаляется через 24 часа. Значения настраиваются через
`UPLOAD_MAX_BYTES`, `UPLOAD_WORKSPACE_QUOTA_BYTES` и
`UPLOAD_UNBOUND_TTL_HOURS`.

## Production

- Используйте внешний TLS reverse proxy или добавьте сертификаты в Nginx.
- Установите `COOKIE_SECURE=true`.
- Задайте отдельные `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` и тот же
  пароль в `DATABASE_URL`.
- Делайте ежедневный backup PostgreSQL и вложений базы знаний, регулярно
  проверяйте восстановление обеих частей.
- Не храните `.env` и API-ключи в Git.
- Перед миграциями создавайте backup и используйте версионированные Docker-образы.

Запуск с production-политиками перезапуска и ограничением Docker-логов:

```bash
docker compose \
  -f docker-compose.yml \
  -f docker-compose.production.yml \
  up -d --build
```

Backup и проверка восстановления:

```bash
./infra/backup.sh
CONFIRM_RESTORE=celestial ./infra/restore.sh \
  backups/celestial-YYYYMMDDTHHMMSSZ.sql.gz \
  backups/celestial-YYYYMMDDTHHMMSSZ-uploads.tar.gz
```

Скрипты на время снимка/восстановления останавливают процессы записи и затем
поднимают их обратно. Для старого дампа, созданного до появления вложений
базы знаний, доступен явный режим `./infra/restore.sh --database-only file.sql.gz`.

Staging использует те же образы и сервисы:

```bash
docker compose --env-file .env.staging -f docker-compose.yml -f docker-compose.staging.yml up --build
```
